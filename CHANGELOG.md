## 0.1.2 - 2026-06-04

- Reframed the LLM-provider model across the spec set: providers are now plug-in code modules in `src/providers/<name>/` (each implementing a `Provider` interface with `onboard` / `login` / `logout` / `discoverModels` / `buildByokConfig` methods and a capability-based flag set), not config-only entries. Per-deployment state lives in `<configDir>/presets/<name>.yaml` and is created by new `copilot-agent provider` CLI subcommands. The Copilot SDK remains the single LLM runtime — providers configure it via BYOK. v1 supports `api_key` and `device_flow` auth methods; full OAuth is reserved for v2. Added `docs/specs/08-providers.md` and made local edits to `00`, `01`, `02`, `03`, `04`, and `07` to rename `provider` → `presetId` where appropriate, add the "plugin code lives in the source tree" cross-cutting principle, document CLI mirrors for the WebUI's `ControlAPI`, and add the "providers are plug-ins, not config blocks" item to the vision.
- Added `docs/specs/` folder with 1 high-level spec (`00-high-level.md`) and 7 boundary specs (`01-channel-adapter.md` through `07-webui-control-surface.md`). Specs describe the target architecture: multi-channel plug-in bot with subprocess-isolated adapters (Telegram, TUI, Discord, future WebUI chat) over stdio+JSON-RPC IPC; `ControlAPI` for the WebUI's non-chat features (session history, agent editor, log tail, config, status, provider/model switcher); soft-TTL session store with cold archive; channel-capability dispatch for stream sinks and permission UI. The existing `docs/ARCHITECTURE/` ADRs remain the current-state record; the two will be reconciled as work lands. Each spec is a target-state design doc, not a description of the current code, and includes open questions with recommended defaults.

## 0.1.1 - 2026-06-04

- Fixed assistant responses never reaching Telegram when the Copilot SDK emits `assistant.message` as an empty completion signal. `onAssistantMessage` in [src/streaming.ts](src/streaming.ts) was unconditionally replacing the accumulated draft with `fullContent`, so when `data.content` was undefined the draft became `''` and the Telegram message reverted to `…`. The sink now only replaces the draft when `fullContent` is non-empty. Additionally, the message handler in [src/telegram.ts](src/telegram.ts) now falls back to `sendAndWait`'s `response.content` when the draft is empty after streaming, ensuring the user always sees the answer even if streaming events were lost or wiped. New regression tests in [src/streaming.test.ts](src/streaming.test.ts).
- Fixed long assistant responses (e.g. multi-file review sessions) silently disappearing in Telegram. `TelegramStreamSink.flushNow` in [src/streaming.ts](src/streaming.ts) was passing the full draft to `editMessageText` with no length cap; when the draft exceeded Telegram's 4096-character limit the API returned `400: message is too long`, the error was swallowed at debug level, and the user was left staring at `…`. `flushNow` now truncates the draft to the last 4093 characters prefixed with `…` when it exceeds the limit, keeping the live message updated. After `sendAndWait` resolves, the message handler in [src/telegram.ts](src/telegram.ts) checks whether the final content (from `response.content` or the accumulated draft) exceeds 4096 characters; if so, it deletes the draft message and sends the full text as properly split chunks via `ctx.reply`. New regression tests in [src/streaming.test.ts](src/streaming.test.ts) and [src/telegram.ts](src/telegram.ts). Architecture doc 001 updated.
- Fixed "Allow once" and "Allow for session" permission buttons doing nothing: the Copilot SDK's `PermissionDecision` wire protocol expects `approve-once` / `approve-for-session` / `denied-interactively-by-user`, not `approved`. The internal `PermissionDecision` kind is now `allow-once` / `allow-session` / `deny`, and `toSdkPermissionResult` in [src/permissions.ts](src/permissions.ts) translates at the SDK boundary. The auto-approve branch in [src/sessions.ts](src/sessions.ts) was also returning the bogus `approved` kind and is now routed through the same mapper. Test coverage added in [src/permissions.test.ts](src/permissions.test.ts). Architecture doc 003 updated to describe the boundary mapping.
- Fixed bot crash on stale permission-button clicks: Telegram only honours `answerCallbackQuery` / `editMessageText` for ~30 seconds after a callback. If the user clicked late (e.g. after the Copilot SDK's 60s `sendAndWait` timeout already killed the session), those API calls returned `400: query is too old`, threw inside grammY middleware, and the unhandled rejection killed the whole bot. The callback handler in [src/telegram.ts](src/telegram.ts) now resolves the permission promise first (which is what actually unblocks the SDK), wraps every Telegram API call in `.catch`, and registers a `bot.catch` error boundary so any future unhandled rejection logs and continues instead of crashing the process.
- Fixed orphaned permission prompts after agent errors: when the message handler caught an SDK error (e.g. the Copilot SDK's `Timeout after 60000ms waiting for session.idle`), any in-flight permission prompt for the same chat was left in the `pendingPermissions` map. The user could still click the buttons, the promise would resolve, but the SDK session was already dead so the agent never resumed — the click appeared to do nothing. The message handler in [src/telegram.ts](src/telegram.ts) now calls a new `cancelPendingPermissions(chatId, reason)` helper on the error path, which resolves all orphan promises with `deny`, removes them from the map, and tells the user the prompts were cleared. The callback handler also now logs an `info` line on entry so future "the callback doesn't happen" reports can distinguish "didn't reach the handler" from "handler ran but the side effect was a no-op".
- Fixed permission prompts racing the SDK's 60s `sendAndWait` timeout: when the agent was blocked on a permission request waiting for the user to click a button, no `session.idle` event fired until the permission resolved. If the user took longer than 60s, the SDK timed out, the session was orphaned, and the user's click arrived too late to be acted on. `SessionManager.sendAndWaitTimeoutMs` in [src/sessions.ts](src/sessions.ts) now caps the SDK timeout at `MAX_SEND_AND_WAIT_MS` (90s) so a hung agent fails fast — decoupled from `permissions.timeout_seconds` which now controls only the user-facing permission window, not the SDK wait. Also: friendly translation of `Timeout after … waiting for session.idle` in the message-handler error path so the user sees "⏳ The model didn't respond in time (90s). Try /model or /new" instead of the raw SDK text. New regression tests in [src/sessions.test.ts](src/sessions.test.ts) lock in the new math.
- Added live streaming of assistant text and tool events to Telegram. New `StreamSink` interface in [src/streaming.ts](src/streaming.ts) (with `noopStreamSink` default) and a `TelegramStreamSink` implementation that edits a single Telegram message in place as the agent streams `assistant.message_delta` chunks, throttled to 750 ms. `onToolStart` appends a `🔧 running \`toolName\` …` status line so the user sees the tool starting before any permission prompt appears. `SessionManager.createSession` in [src/sessions.ts](src/sessions.ts) registers an `onEvent` hook that dispatches SDK events to the per-chat active sink. `enqueueMessage` accepts an optional sink and detaches it in a `finally` block. `TelegramBot` creates a fresh sink per user message, aborts the previous sink if a new message arrives mid-stream, and edits the same message for final errors and "no response" hints. New test files: [src/streaming.test.ts](src/streaming.test.ts) (11 tests) and 8 new dispatch tests in [src/sessions.test.ts](src/sessions.test.ts). Architecture doc 001 updated with a "Streaming Assistant Output" section.
- Implemented the feature per the plan in [docs/superpowers/plans/2026-06-04-streaming-assistant-output.md](docs/superpowers/plans/2026-06-04-streaming-assistant-output.md).
- Fixed permission prompts going silent after a bot restart. Previously, when `tsx watch` (or any process restart) killed the bot while a permission prompt was on screen, the in-memory `pendingPermissions` map was lost — the user would click the button, the new process would receive the callback, look up the (now-empty) map, and silently do nothing. The handler did try to answer with "⏰ This prompt has expired.", but the query was already past Telegram's 30-second TTL, so `answerCallbackQuery` returned 400 and the user saw no feedback. New `persistPendingPermissions` and `rehydratePendingPermissionsFromDisk` in [src/telegram.ts](src/telegram.ts) write the `pendingPermissions` map to `<configDir>/pending-permissions.json` on every set/delete and rehydrate it on startup. Each rehydrated record is edited in-place on Telegram to either "⚠️ interrupted by a bot restart, please resend" (within `timeout_seconds`) or "⏰ has expired" (past the timeout), so the user always gets clear feedback. New 5 tests in [src/telegram.test.ts](src/telegram.test.ts) cover the no-file, fresh-orphan, expired-orphan, corrupted-JSON, and tool-name-capitalisation cases. `index.ts` now passes `configDir` to the `TelegramBot` constructor.
- Added `AGENTS.md` with build/test commands, source layout, conventions, architecture index, pitfalls, and feature-addition workflow
- Added IMPORTANT note in `AGENTS.md` requiring granular CHANGELOG entries on every change and docs ↔ code parity checks
